Signature Initiative

Customer Service Hub — a production Databricks Lakehouse, deployed as code

Outcome 6 production workflows · 3 workspaces · 140 tests Notebooks, jobs, permissions & schema shipped atomically through CI/CD

Built and operate the Lakehouse that consolidates customer-support and engagement data — voice, chat, order events, cases and customer master data — into Unity Catalog for operational reporting, AI-driven interaction classification and PII-safe analytics. Every schema change, job and permission is version-controlled and promoted Dev → Stage → Prod by pipeline, never by hand.

Problem

  • Support and engagement data was spread across voice, chat, order-event and case systems, with no single governed place to analyse it.
  • Notebook and job deployment depended on a separate Git-sync process, so code and job definitions could drift apart between environments.
  • Unity Catalog schema changes were applied manually — a risk in Production and a bottleneck with several developers working in parallel.
  • Customer transcripts contain PII and had to be safe to analyse before anyone could classify or report on them.

Approach

  • CI/CD as code: a 4-stage Azure DevOps pipeline (Validate → Dev → Stage → Prod) deploying Databricks Asset Bundles with per-environment service principals, approval gates and a single validated artefact reused everywhere.
  • Bundle generator: Python tooling that assembles databricks.yml from per-job YAML, enforces naming rules, catches duplicates and missing notebooks at build time, and applies job permissions consistently.
  • Schema reconciliation engine: diffs version-controlled DDL against the live catalog, auto-applies safe changes (new columns, type widening) and routes destructive or ambiguous drift to a conditional review gate that blocks only in Production.
  • Ingestion & AI: metadata-driven, watermark-based ingestion; Azure Service Bus → Auto Loader every 15 minutes; GPU PII masking (XLM-RoBERTa + Presidio) followed by AI_CLASSIFY interaction categorisation.

Outcome

  • 6 production Databricks Workflows live across 3 workspaces, running every 15 minutes to daily.
  • Atomic deployments: notebooks, jobs and permissions ship together; the separate Git-sync dependency is gone.
  • 1,042 → 228 lines of pipeline YAML through reusable templates; 140 pytest tests run on every build.
  • Governance enforced in CI: six DDL rules; 40 tables, 20 routines and 2 views remediated in one pass.
  • Safe schema evolution without blocking parallel work in Dev/Stage, and human review where it matters in Prod.

Customer Service Hub data flow — ingest, protect, classify, serve

Problem. Voice, chat, order-event, case and customer master data lived in separate systems, and interaction transcripts carried PII that made them unsafe to analyse as-is.

Approach. Land order events from Azure Service Bus as parquet and pick them up with Auto Loader; drive every other source through a config-table ingestion framework with watermarks; layer data raw → staging → processed in Unity Catalog; mask PII on GPU before any LLM classification touches a transcript.

Outcome. A governed Lakehouse serving operational reporting, engagement insight and AI-classified interactions — with new sources onboarded by configuration rather than new code, and the whole stack promoted Dev → Stage → Prod by pipeline.

  • FreshnessOrder events every 15 minutes
  • ReliabilityWatermark loads · idempotent reprocessing
  • PrivacyPII masked before classification
  • GovernanceUnity Catalog · DDL rules enforced in CI
